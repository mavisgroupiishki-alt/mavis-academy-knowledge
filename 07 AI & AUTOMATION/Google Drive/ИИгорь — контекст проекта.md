﻿ИИГОРЬ — ПОЛНЫЙ КОНТЕКСТ ПРОЕКТА
ТЗ, архитектура, сделанное, проблемы, ошибки, текущий статус и следующий план работ


1. ЧТО ЭТО ЗА ПРОЕКТ


«ИИгорь» — внутреннее веб-приложение Mavis Group для автоматизации работы экспертов и оформителей при подготовке пакетов документов.


Главная задача проекта:
получить от клиента исходные документы → распознать и структурировать информацию → сохранить её в карточке компании → автоматически сформировать корректный пакет документов по выбранной услуге → подсветить только реальные сомнения → сохранить результат и знания для последующих обращений.


ИИгорь не должен быть просто чатом, который генерирует текст. Он должен работать как управляемый ИИ-оформитель:
• ИИ распознаёт и понимает документы;
• данные сохраняются в структурированном виде;
• бизнес-правила исполняются кодом;
• утверждённые Word-шаблоны сохраняют структуру и оформление;
• отсутствующие сведения не выдумываются;
• сомнительные места показываются пользователю;
• исправления и регламенты можно сохранять как знания;
• при повторной работе по компании информация не собирается заново.


2. ТЕХНОЛОГИЧЕСКАЯ БАЗА


Текущий проект разворачивается через:
• GitHub — основной репозиторий проекта;
• Render — backend и deploy;
• Python backend;
• HTML/JavaScript frontend — основной интерфейс в index.html;
• python-docx и работа с DOCX-шаблонами;
• openpyxl/xlrd для Excel;
• AI/Vision для распознавания документов и сканов;
• ZIP/RAR — обработка архивов;
• Word / Excel / PDF / изображения;
• серверное JSON-хранилище;
• предусмотрен Persistent Disk Render с mount path /data;
• локальное сохранение карточек в браузере как резервный слой.


Репозиторий, с которым велась работа: mavisgroupiishki-alt/iso-smk.

9. КРИТИЧЕСКАЯ ОШИБКА ОБУЧЕНИЯ


В тестах была обнаружена важная проблема:
пользователь пишет «исправь» или «обучись», а ИИгорь отвечает «да, всё исправил», но фактически в карточке или новом пакете ничего не меняется.


Это считается критической ошибкой.


Правильное поведение:
• сравнить данные до и после правки;
• если данные реально изменились — подтвердить;
• если не изменились — прямо написать, что правка не применилась;
• нельзя обещать «всё исправлено» без фактического результата;
• сохранённое правило должно доходить до генератора документов, а не жить только в переписке.


10. СТИЛЬ ОТВЕТОВ ИИГОРЯ

• API;
• hardcoded;
• названия переменных;
• внутренние поля;
• endpoint;

• «очистите кэш»;
• выдуманные технические причины.


Ответ должен быть понятен эксперту или оформителю.


11. КАЛЬКУЛЯТОР СТАЖА


Нужна отдельная вкладка «Расчёт стажа».


Главное требование:
стаж должен считаться самостоятельно по трудовой, а не подставляться из старой готовой Формы №2.


Алгоритм:
1) распознать записи трудовой;
2) распознать вкладыши;
3) взять реальные даты;
4) определить организацию;
5) определить должность;
6) сформировать периоды;
7) определить, относится ли период к заявляемой специализации;
8) исключить нерелевантные периоды;
9) объединить пересекающиеся периоды;
10) не удваивать параллельные периоды;
11) отдельно посчитать общий релевантный стаж;
12) отдельно посчитать стаж в текущей организации.


Запрещено придумывать 01.01, если в документе указан только год.


Если точная дата неизвестна — это должно быть видно пользователю.


11.1. Интерфейс калькулятора
Нужно:
• выбрать компанию;
• выбрать сотрудника;
• загрузить трудовую;
• загрузить вкладыш;
• увидеть распознанные периоды;
• вручную исправить период;
• включить/исключить период;

• пересчитать;
• сохранить сотруднику;

15. СПК — ОСНОВНЫЕ НАЙДЕННЫЕ ПРОБЛЕМЫ


При аудите обнаружено:
• распознанные данные не всегда доходили до генератора;
• Справка СИ могла содержать выдуманные рулетку и уровень;
• поверки были фиктивными;
• ТТК генерировались как ТТК-001 / ТТК-002;
• фигурировал выдуманный разработчик;
• прораб мог становиться главным инженером;
• из ИТР терялись диплом, стаж, трудовая, аттестат;
• в паспорте оставались данные старой компании;
• площадь помещений бралась из шаблона;
• в БИСП оставался «Кастом-Инвест»;
• перечень продукции не зависел от реальных видов работ;
• часть ошибок генерации скрывалась от пользователя.

17. БОЛЬШИЕ ТРУДОВЫЕ И PDF


Критическая проблема аттестации/СПК:
большие трудовые считываются тяжело, не все файлы загружаются, обработка может идти долго.


Проводились оптимизации:
• большой PDF переводить в фоновую обработку;
• трудовые читать до большого количества страниц;
• увеличить допустимый размер PDF внутри ZIP;
• не читать большую трудовую дважды целиком;
• тяжёлые PDF обрабатывать последовательно;
• большие фото уменьшать перед отправкой;
• уменьшать vision batch;
• не тратить время на неэффективный OCR больших рукописных трудовых перед Vision.


Это направление ещё требует полноценного нагрузочного тестирования.


18. УНИВЕРСАЛЬНЫЙ РАЗБОР АРХИВА


Была проблема: документы, лежащие не в персональной папке, могли теряться.


Например ISO-архив содержал:
• перечень поставщиков;
• перечень объектов;
• реквизиты;
• список сотрудников XLS;
• удостоверения по охране труда.


ИИгорь должен:
• видеть все физические файлы;
• читать XLS/XLSX;
• читать Word;
• читать PDF;
• читать изображения;
• сохранять тематические документы;
• не говорить «файла нет», если файл физически существует.


Отдельная ошибка: строка [Лист: TDSheet] в успешно прочитанном XLS ошибочно считалась ошибкой чтения. Это исправлялось.


19. ЖЁЛТАЯ ПОДСВЕТКА


Очень важное требование:
НЕ нужен отдельный файл со списком проблем.


Нужно выделять жёлтым непосредственно внутри сформированного DOCX только конкретное значение, которое:
• отсутствует;
• распознано неуверенно;
• конфликтует с другим документом;
• осталось шаблонным;
• требует ручной проверки.


20. ЧТО НЕ НАДО КРАСИТЬ ЖЁЛТЫМ


Была серьёзная ошибка — документы получались почти целиком жёлтыми.


Причины:
• старое жёлтое форматирование уже было в шаблонах;
• одно сомнение могло закрасить всю строку;
• низкая общая OCR-confidence могла закрасить все сведения сотрудника.


Требование:
• старую жёлтую заливку шаблона сначала очищать;
• потом наносить новую точечно;
• если сомнителен номер удостоверения — жёлтый только номер;
• не закрашивать ФИО, должность, всю строку и всю таблицу без причины.


21. ISO/СУОТ — ШАБЛОН «ВАРТА»


Крупнейший источник исторических ошибок — пакет компании ООО «Варта» использовался как база шаблонов.


Из-за этого оставались:
• «Варта»;
• сотрудники «Варты»;
• область «Варты»;
• даты;
• реквизиты;
• процессы;
• колонтитулы.


22. «ВАРТА» В КОЛОНТИТУЛАХ


Особенно упорная ошибка.


Основной текст заменялся, но в header/footer оставалось «ООО «Варта»».


Причина: Word может хранить одно слово в нескольких XML-runs, например «Вар» + «та».


Была добавлена отдельная очистка сложных колонтитулов и текстовых блоков.


Ещё одна ошибка: простой поиск «Варта» мог ложно реагировать на слово «квартал». Проверку нужно делать именно по названию компании, а не произвольной подстроке.


23. ISO/СУОТ — СОТРУДНИКИ


Нельзя заменять сотрудников позиционно:
«первый ИТР → первый человек шаблона».


Нужно связывать:
ФИО + фактическая должность + назначенная роль.


Особенно важно для приказов и ответственных лиц.


24. ISO/СУОТ — ИНСТРУКЦИИ


Обратная связь оформителя:
ИИгорь запрашивал у пользователя готовые инструкции по профессиям.


Правильное поведение:
• если штат и профессия известны — инструкции формировать автоматически;
• должностные инструкции ИТР — по фактической должности;
• инструкции по охране труда рабочих — по фактической профессии;
• не требовать у пользователя готовый документ как обязательный исходник, если его можно сформировать по заложенной логике;
• если точного специального шаблона нет — сделать редактируемый рабочий проект, но не оставлять бессмысленное «дополнить профильными обязанностями».


25. ISO/СУОТ — ПОСТАВЩИКИ


Была проблема: перечень поставщиков распознавался, но итоговые карточки:
• были почти пустыми;
• не соответствовали исходному рабочему шаблону;
• могли содержать фиктивного конкурента;
• оценка не была понятна.


Требование:
• брать фактическое название поставщика;
• брать фактическую продукцию;
• сохранять структуру утверждённого шаблона;
• не выдумывать баллы;
• если оценки нет — оставить один понятный пункт на проверку, а не десятки жёлтых клеток.


26. ISO/СУОТ — ПРИКАЗЫ


Последняя обнаруженная ошибка:
ИИгорь начал формировать один и тот же приказ в двух вариантах:
• старый вариант;
• новый вариант.


При этом старый вариант содержал более подробную рабочую формулировку.


Требование:
• формировать только один приказ каждого назначения;
• не выдавать старую и новую копию одновременно;
• приоритет — актуальному рабочему шаблону с более полной корректной формулировкой;
• не дублировать документ только потому, что найдено несколько шаблонов.


Последняя правка по этой ошибке вносилась в generator_iso_suot_templates.py.


27. ISO/СУОТ — ОБЛАСТЬ В РК СМК


Последняя обратная связь:
в РК СМК ИИгорь сам добавлял «разработка проектной документации» к области организации.


Это неправильно.


Жёсткое правило:
«разработка проектной документации» добавляется ТОЛЬКО если:
• она прямо указана в исходных данных;
• входит в заявленную область;
• либо пользователь явно просил её включить.


ИИгорь не имеет права самостоятельно расширять область организации на основании шаблона, должностей, документов или предполагаемой деятельности.


28. ПРОГРАММА ВНУТРЕННИХ АУДИТОВ


По последнему тесту программа аудитов формируется нормально.


Текущую рабочую логику программы аудитов менять без необходимости не нужно.


29. ISO/СУОТ — ДРУГИЕ ПРОБЛЕМЫ, КОТОРЫЕ УЖЕ НАХОДИЛИ


• неправильные ФИО/должности в приказах;
• сотрудники из шаблонной компании;
• область сертификации старой компании;
• даты старого шаблона;
• должностные инструкции без профильного содержания;
• рабочие инструкции не по фактическому штату;
• карточки поставщиков не по шаблону;
• слишком много жёлтого;
• «Варта» в колонтитулах;
• ложное предупреждение о «Варте»;
• пользовательская правка через обучение не влияла на генерацию.


30. СКОРОСТЬ


Одна из главных жалоб:
формирование могло идти около 30 минут.


Особенно тяжёлые сценарии:
• аттестация;
• большие трудовые;
• много сканов;
• большое количество сотрудников.


Для ISO/СУОТ делался ускоренный режим:
• меньше AI-вызовов;
• более короткий продуктовый промпт;
• не делать отдельный AI-вызов на каждого сотрудника без необходимости;
• не запускать старый медленный fallback;
• уменьшать объём Vision-обработки там, где это допустимо.


Цель: активное время пользователя должно сокращаться, а техническая обработка не должна занимать десятки минут на обычный пакет.


31. ВЕРСИЯ ПРИЛОЖЕНИЯ


Была добавлена идея показывать версию прямо в интерфейсе.


Пример:
ИИгорь v18.1 · короткий SHA коммита.


Задача:
• понимать, что Render действительно задеплоил новый код;
• видеть совпадение frontend/backend;
• не тестировать случайно старую версию из кэша.


32. RENDER


Было замечено:
• Auto-Deploy был выключен;
• затем его включили;
• deploy запускали вручную.


Также Render несколько раз показывал:
Ran out of memory — over 512 MB.


Это важно для обработки больших PDF и архивов.


Нужно продолжать следить за RAM, особенно при Vision и параллельной обработке файлов.

34. МЕТРИКИ ПРОЕКТА «ДО / ПОСЛЕ»


По таблице оформителей были использованы действующие оформители Кристина и Настя.


База по объёму:
примерно 83 пакета в месяц по продуктам, которые должен покрывать ИИгорь.


Средние времена ДО по вводным оформителя:
• СПК — 40–50 минут, для расчёта брали 45 минут;
• ISO — около 60 минут;
• СУОТ — около 90 минут;
• Аттестация — около 90 минут, если не более 10 человек.


Если информация приходит частями, календарный срок может растягиваться на 1–2 дня, но это ожидание исходных данных, а не активное ручное время.


Плановые времена ПОСЛЕ до полноценного пилота:
• СПК — 15 минут ручного времени;
• ISO — 15 минут;
• СУОТ — 20 минут;
• Аттестация — 20 минут.


Расчёт:
• ручное время ДО ≈ 101 ч/мес.;
• ПОСЛЕ план ≈ 24,7 ч/мес.;
• высвобождение ≈ 76,4 ч/мес.;
• снижение ручных трудозатрат ≈ 75,6%;
• ≈ 916,5 ч/год;
• ≈ 0,45 FTE.


Средняя зарплата одного оформителя для денежного эквивалента:
• Кристина — около 1 152 BYN;
• Настя — около 890 BYN;
• средняя — 1 021 BYN;
• при 168 рабочих часах стоимость часа ≈ 6,08 BYN.


Денежный эквивалент высвобождённого времени:
• около 464 BYN/мес.;
• около 5 570 BYN/год.


Это не прямое сокращение ФОТ, а стоимость высвобождённого времени.


Ошибки оформления ДО:
• примерно 2,3 доработки/мес. по продуктам ИИгоря, если считать случаи, где фигурирует оформитель;
• около 2,7% пакетов.


Целевой показатель ПОСЛЕ:
• ≤1 доработка/мес.;
• ≤1% доля доработок.


Порог «меньше 5 ошибок» можно оставить как абсолютный контрольный максимум, но он слабее фактической исторической базы.


35. ЧТО СЧИТАТЬ ГОТОВЫМ РЕЗУЛЬТАТОМ ПРОЕКТА


ИИгорь считается готовым к полноценной работе, когда:
• архив стабильно разбирается;
• большие документы читаются;
• карточка компании не теряет данные;
• обучение действительно влияет на новые пакеты;
• стаж рассчитывается самостоятельно;
• ISO/СУОТ не содержит «Варту»;
• приказы не дублируются;
• область не расширяется самовольно;
• поставщики формируются по шаблону и факту;
• инструкции соответствуют реальному штату;
• СПК не содержит выдуманных СИ/ТТК/поверок;
• аттестация сохраняет трудовые, вкладыши, дипломы и аттестаты;
• жёлтый цвет используется минимально и точечно;
• пользователь получает понятный ответ без технических терминов;
• обычный пакет не обрабатывается десятки минут;
• новый deploy легко идентифицируется по версии.


36. ЧТО ЕЩЁ НЕ СЧИТАЕТСЯ ПОЛНОСТЬЮ ЗАКРЫТЫМ


Несмотря на большое количество внесённых правок, нужны реальные повторные тесты на нескольких компаниях.


Необходимо ещё проверить:
• ISO отдельно;
• СУОТ отдельно;
• ISO+СУОТ;
• СПК Стройкомплекс;
• СПК БИСП;
• аттестацию компании;
• аттестацию специалиста;
• большую трудовую;
• компанию с большим штатом;
• компанию без части данных;
• повторную компанию из сохранённой карточки;
• работу обучения на новом клиенте.


37. КРИТИЧНЫЙ ЧЕК-ЛИСТ ДЛЯ СЛЕДУЮЩЕГО РАЗРАБОТЧИКА / НОВОГО ЧАТА


Перед любыми новыми изменениями:
1. Работать только с актуальным архивом/репозиторием, а не со старой промежуточной сборкой.
2. Не ломать уже работающую программу аудитов.
3. Не возвращать старую глобальную замену шаблонов.
4. Не придумывать данные.
5. Любая правка пользователя должна иметь проверяемый фактический результат.
6. Неполный AI-ответ не должен стирать ранее найденные данные.
7. Жёлтое выделение — только точечное.
8. Тестировать Word не только по document.xml, но и header/footer, таблицам и сложным runs.
9. Проверять старые шаблонные компании:
   • Варта;
   • МонТехБел;
   • Кастом-Инвест;
   • Сфера Секьюрити;
   • и другие используемые эталонные компании.
10. Для ISO/СУОТ область организации всегда брать из фактического запроса.
11. Не дублировать одинаковые документы.
12. Приказы формировать с корректными ФИО + должностями.
13. СПК — только реальные СИ/поверки/ТТК.
14. Стаж — считать из трудовой.
15. После каждого исправления прогонять регрессионный тест по всем продуктам.


38. ПОСЛЕДНЯЯ ИЗВЕСТНАЯ ПРАВКА


Наиболее свежая конкретная задача была по ISO/СУОТ:
• убрать дублирование приказов;
• оставить один более полный рабочий вариант;
• убрать автоматическое добавление «разработка проектной документации» в область РК СМК;
• не расширять область без запроса организации;
• программу аудитов оставить как есть.


Эта правка была внесена в generator_iso_suot_templates.py поверх последнего присланного пользователем актуального архива.


39. ОБЩИЙ ПРИНЦИП ПРОЕКТА


ИИгорь должен не «красиво отвечать», а выдавать воспроизводимый правильный результат.


Приоритеты в таком порядке:
1. достоверность данных;
2. отсутствие выдуманных сведений;
3. сохранение правильного шаблона;
4. минимальная ручная работа;
5. понятная проверка сомнений;
6. скорость;
7. накопление знаний и данных компании.


Финальная модель работы:
архив клиента → распознавание → структурированная карточка → проверка комплектности → расчёты → формирование → автоматическая проверка → точечные жёлтые места → финальный пакет → сохранение знаний и карточки.
